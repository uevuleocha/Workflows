# Skill Portability + Adoption One-Shot Prompt

**What this is:** a copy-paste prompt for helping an agent inspect, generalize, and adoption-proof a reusable skill before it is shared, cloned, forked, or made public.

Use this when a skill was originally built for one person's machine, paths, APIs, workspace layout, or habits, and you want another user to adopt it cleanly on their own Windows, macOS, or Linux setup.

The goal is not to remove all personal defaults. The goal is to separate maintainer defaults from universal behavior, document setup clearly, and make the skill safe for another user and their agent to adapt.

---

## Copy-Paste Prompt For The Agent

You are helping me adoption-proof a reusable agent skill.

Read the skill folder I point you to, including `SKILL.md`, `README.md` if present, `agents/openai.yaml`, scripts, prompt files, and referenced resources.

Your job is to inspect the skill for portability issues and propose or make improvements so another user can safely adopt it on their own machine.

Do not assume the original maintainer's paths, operating system, workspace names, API keys, repo names, or folder conventions apply to me.

### First Explain The Goal

Before editing, explain this in plain language:

1. Some skills are universal.
2. Some skills contain maintainer-specific defaults, paths, or examples.
3. Maintainer defaults are okay when clearly labeled.
4. Universal instructions should use host workspace, user home, environment variables, or user-confirmed paths.
5. If a skill needs API keys, packages, or private setup, it should guide the agent to create a setup task rather than exposing secrets or guessing.
6. If a skill needs a local master skills folder, the user should normally choose one canonical local master per machine unless they explicitly want multiple.

### Required Inspection Areas

Check for:

- hard-coded absolute paths
- Windows-only assumptions
- macOS/Linux incompatibilities
- workspace-specific language, such as one person's project name
- private GitHub usernames or repo URLs
- API keys, token names, setup assumptions, or secret-handling risks
- references to local task, archive, summary, or output folders
- generated files such as `__pycache__`, `.pyc`, build output, logs, or local artifacts
- whether a README would help a new user adopt the skill
- whether `SKILL.md` itself contains the operational adoption rules, not only the README

### Local Master Skills Folder Rule

If this skill creates, edits, or syncs other skills, enforce this rule:

By default, a machine should have one canonical local master skills folder. The local master is the source of truth before syncing to global agent installs.

The local master may live in a dedicated skills workspace, such as `Uzzy Skills`, `John Skills`, or another user-named workspace, or as a `skills/` folder inside an existing workspace.

Once the user chooses it, treat it as the default rule for that user's machine. Do not create or use multiple local master folders unless the user explicitly asks for a multi-master setup.

### Path Handling Rule

Use host-aware paths:

- Prefer `<project root>/...` for workspace-relative paths.
- Prefer `~/.codex/skills`, `~/.claude/skills`, and `~/.gemini/config/skills` as candidates, not assumptions.
- On Windows, show Windows examples.
- On macOS/Linux, show POSIX examples.
- If a path does not exist, ask whether to create it, skip it, or use another path.

### Setup-Gated Skills

If the skill needs an API key, package install, CLI login, model provider, or private configuration:

- do not ask the user to paste secrets into chat
- do not print or save secret values
- add a setup gate before real execution
- add or update README setup guidance
- route missing prerequisites to the host workspace's configured task directory
- use `<project root>/Archive/Tasks/` or `<project root>\Archive\Tasks\` only as a common default, not a universal rule

### README Guidance

Add or update `README.md` when a new user would benefit from adoption instructions.

The README should include:

- what the skill does
- what setup is needed
- what paths must be configured
- what the agent should ask the user
- what must never be exposed, such as API keys
- OS adaptation notes for Windows/macOS/Linux
- a copy-paste adoption prompt for the user's agent

Keep `SKILL.md` as the operational source of truth. Do not put required behavior only in README.

### Output Format

Report:

1. Skill inspected
2. Portability issues found
3. Which issues are intentional maintainer-specific defaults
4. Suggested `SKILL.md` edits
5. Suggested README additions
6. Files that should not be shared
7. Validation steps
8. Whether the skill is ready to share

### Definition Of Done

The skill is adoption-ready when:

- maintainer-specific defaults are labeled as examples
- universal behavior does not depend on one user's absolute paths
- path discovery works across Windows/macOS/Linux
- API/setup gates are clear
- README adoption guidance exists where useful
- `SKILL.md` contains the actual operational rules
- generated/local files are excluded
- local and global copies are synchronized if the user requested sync
- validation passes

### Failure Conditions

This adoption pass has failed if:

- the agent assumes the original maintainer's paths apply to the adopter
- the agent removes useful maintainer defaults instead of labeling them clearly
- required behavior exists only in README and not in `SKILL.md`
- the skill still requires one user's absolute paths for normal use
- setup-gated skills can reach paid/API execution before prerequisites are checked
- API keys, tokens, or secret values are requested in chat, printed, or saved
- generated files such as `__pycache__` or `.pyc` are treated as source
- the agent creates multiple local master skills folders without explicit user intent
- the final report does not state whether the skill is ready to share

## Quick Checklist

- [ ] Read `SKILL.md` fully.
- [ ] Read `README.md` if present.
- [ ] Read `agents/openai.yaml` if present.
- [ ] Read scripts, prompt files, and referenced resources that affect setup or paths.
- [ ] Identify maintainer-specific defaults.
- [ ] Label useful maintainer defaults as examples, not universal paths.
- [ ] Replace universal behavior with host-aware or user-confirmed paths.
- [ ] Preserve one canonical local master skills folder per machine unless the user asks for more.
- [ ] Add or update README adoption guidance where useful.
- [ ] Keep operational rules in `SKILL.md`.
- [ ] Check for generated files and local artifacts that should not be shared.
- [ ] Validate the skill after edits.
- [ ] Sync global copies only if the user requested sync.

---

## One-Line Summary

**Adoption-proofing a skill means keeping useful maintainer defaults while making universal behavior portable, explicit, setup-gated, and safe for another user's machine.**
