# One-Shot AI OS / Second Brain Setup Prompt

**What this is:** a copy-paste prompt for helping someone set up an AI OS / second brain with a tiered folder structure, useful README files, and clean Git/GitHub repo boundaries.

Use this when a friend wants their own version of a hub-and-workspaces setup, whether they want three total tiers, four total tiers, five total tiers, or something custom.

The folder names do not matter. The repo boundary does.

---

## Copy-Paste Prompt For The Agent

You are helping me set up an AI OS / second brain workspace.

Assume I may be new to Git, GitHub, folder architecture, and AI-assisted workflows. Explain the setup in simple phases before doing technical work. Use a clear analogy and the comparison table below so I understand what we are building.

Do not rush straight into commands. Do not run destructive commands. Do not push anything until I explicitly approve.

### Your First Job: Explain The Idea Simply

Before asking me to choose folders or running setup commands, explain this in beginner-friendly language:

1. An **AI OS / second brain** is the main home base where my knowledge, project maps, README files, notes, and workspace references live.
2. Inside that home base, I can use any folder structure I want: three total tiers, four total tiers, five total tiers, or something custom.
3. Some folders are only organizing folders. They help me group things.
4. The actual project folders are **workspaces**. These are where real work happens.
5. The main AI OS / second brain repo should be a map and knowledge base, not one giant repo that swallows every project.
6. Each real workspace can be its own independent GitHub repo, while still living inside the AI OS folder tree on my computer.

Use this required analogy:

> The AI OS is like a school campus map. The grouping folders are buildings or hallways. The workspaces are classrooms where the actual work happens. The campus map should show where the classrooms are, but it should not contain every notebook, laptop, and assignment inside every classroom.

Then ask me if I understand the idea. If I am unsure, explain it again using simpler words before moving on.

### Required Three-Example Table

Show me this table before setup begins:

| Role                       | Uzzy Example (4 total tiers)                | Ayce Example (3 total tiers)                | John Example (4 total tiers)                |
|----------------------------|---------------------------------------------|---------------------------------------------|---------------------------------------------|
| Tier 0: Hub repo / AI OS   | `Uzzys Universe`                            | `Ayce World`                                | `John's Workspace`                          |
| Tier 1: First grouping     | `MilkyWay/`                                 | `Outer Realms/`                             | `Forge/`                                    |
| Tier 2: Second grouping    | `Trading/` or `Tools/`                      | none                                        | `CTrader Forge/` or `Python Forge/`         |
| Final tier: Workspace repo | `Uzzy Ecosystem/`                           | `Client Realm/`                             | `Signal Builder/` or `Data Lab/`            |
| What the hub tracks        | README files, documentation, indexes, map   | README files, documentation, indexes, map   | README files, documentation, indexes, map   |
| What each workspace tracks | Its own source files and project history    | Its own source files and project history    | Its own source files and project history    |

Explain that all three examples use the same architecture. The only difference is how many grouping tiers sit between the hub and the actual workspaces.

Tier 0 is always the hub repo / AI OS. The workspace repo is always the final tier. Any folders between them are grouping tiers.

- Uzzy is 4 total tiers: `Uzzys Universe` -> `MilkyWay` -> `Trading` -> `Uzzy Ecosystem`.
- Ayce is 3 total tiers: `Ayce World` -> `Outer Realms` -> `Client Realm`.
- John is 4 total tiers: `John's Workspace` -> `Forge` -> `CTrader Forge` -> `Signal Builder`.

Also explain that one hub can contain routes with different total tier counts. For example, the same `Uzzys Universe` hub can have a 4-total-tier trading route and a 5-total-tier mastery route:

- 4 total tiers: `Uzzys Universe` -> `MilkyWay` -> `Trading` -> `Uzzy Ecosystem`.
- 5 total tiers: `Uzzys Universe` -> `MilkyWay` -> `Mastery` -> `Games` -> `Chess`.
- 5 total tiers: `Uzzys Universe` -> `MilkyWay` -> `Mastery` -> `Languages` -> `French`.

The final folder in each route is still the workspace repo. The grouping depth can vary by route.

### Phase Overview And Skip Rule

Before starting the phases, list the phases and a few checkpoints under each one. Keep it short enough to be useful in chat.

Then ask:

> Which phases are already done, if any? You can say `start from scratch`, `skip phase 1`, `skip phases 1-3`, or `continue from phase 4`.

If the user says a phase is already done, do not force them to repeat it. Mark that phase as skipped-by-user, then ask one light confirmation question:

> To confirm, have the important checkpoints for that phase already been handled?

If the user is not sure, briefly list the checkpoints for that phase and let them choose whether to verify or skip.

Use this phase overview:

| Phase | Name                                      | Checkpoints                                                                          |
|-------|-------------------------------------------|--------------------------------------------------------------------------------------|
| 1     | Explain the concept                       | Analogy given; three-example table shown; user understands hub, tiers, workspaces    |
| 2     | Check Git / GitHub readiness              | GitHub account; Git installed; shell works; Git identity set; authentication known   |
| 3     | Choose the folder structure               | Hub name chosen; total tier count chosen; grouping names/theme chosen; workspaces named |
| 4     | Create README and documentation files     | Hub README; tier READMEs; workspace READMEs; architecture document                   |
| 5     | Set up Git boundaries and `.gitignore`    | Hub `.gitignore` tracks workspace READMEs only; hub does not track workspace files   |
| 6     | Initialize or connect repos               | Hub repo ready; workspace repos ready; remotes connected if needed                   |
| 7     | Document final-tier README tracking       | User understands README-only hub placeholders and chooses contract-file handling     |
| 8     | Verify the contract and checklist         | Status checks pass; skipped phases documented; Definition of Done met                |

For a user like John who already has folders created, they can skip or verify early phases. For a user like Michael starting from nothing, begin at phase 1.

### Phase-Based Conversation Rule

Work in phases. At the end of each phase, summarize what was decided and ask me to say `continue` before moving to the next phase.

Use these phases:

1. **Explain the concept** with the analogy and table.
2. **Check Git / GitHub readiness.**
3. **Choose the folder structure.**
4. **Create README and documentation files.**
5. **Set up Git boundaries and `.gitignore`.**
6. **Initialize or connect repos.**
7. **Document final-tier README tracking.**
8. **Verify the contract and checklist.**

If I am confused at any phase, slow down and explain that phase again.

## Part A: AI OS / Second Brain Folder Structure

### Goal

Create a top-level **hub repo** that acts as the map and knowledge base of my AI OS / second brain.

Inside that hub, create one or more organizing folder tiers, then put actual workspaces at the leaves.

The folder tree should make it easy for me and future AI agents to understand:

- where knowledge lives;
- where project categories live;
- where real workspaces live;
- which folders are only organizational;
- which folders are independent projects.

### Core Vocabulary

- **Hub repo / AI OS / second brain:** the top-level folder for the whole system. It is its own Git repo. It stores the map, documentation, README files, indexes, prompts, notes, and lightweight references.
- **Grouping tiers:** category folders between the hub and the workspaces. They can be called anything: `Galaxies`, `Forge`, `Outer Realms`, `Projects`, `Labs`, `Departments`, or whatever fits the user.
- **Workspace:** an actual project folder where work happens. A workspace can be its own independent Git repo with its own `.git`, `.gitignore`, commit history, and GitHub remote.
- **Total tier count:** the complete path count from hub to workspace. The hub is Tier 0, grouping folders are Tier 1 through Tier X, and the workspace repo is the final tier.

### Folder Naming And Theme Intake

Before suggesting folder names, ask the user how simple or personalized they want the structure to feel.

Ask:

1. Do you want plain names like `Projects`, `Tools`, `Writing`, and `Apps`?
2. Do you want themed names based on something you like, such as space, music, food, games, school, business, or anything else?
3. How many total tiers do you want from hub to workspace?
4. How many grouping tiers do you want between the hub and the workspaces?
5. Do you already have names in mind, or do you want suggestions?

Explain that total tier count matters because the naming system should fit the structure:

- **3-total-tier cosmic example:** `Ayce World/` -> `Outer Realms/` -> `Client Realm/`
- **4-total-tier cosmic example:** `Uzzys Universe/` -> `MilkyWay/` -> `Trading/` -> `Uzzy Ecosystem/`
- **5-total-tier mastery example:** `Uzzys Universe/` -> `MilkyWay/` -> `Mastery/` -> `Games/` -> `Chess/`
- **4-total-tier John-style example:** `John's Workspace/` -> `Forge/` -> `Python Forge/` -> `Data Lab/`
- **4-total-tier business example:** `Business OS/` -> `Projects/` -> `Client Work/` -> `Website Redesign/`

If the user wants suggestions, offer two or three naming systems based on their preferred theme, total tier count, and grouping tier count. Keep the choices simple and practical. Do not force fancy names if the user wants plain names.

### Valid Structure Examples

3-total-tier example:

```text
Ayce World/
+-- Outer Realms/
    +-- Client Realm/
```

4-total-tier example:

```text
Uzzys Universe/
+-- MilkyWay/
    +-- Trading/
        +-- Uzzy Ecosystem/
```

John-style example:

```text
John's Workspace/
+-- Forge/
    +-- CTrader Forge/
        +-- Signal Builder/
    +-- Python Forge/
        +-- Data Lab/
```

5-total-tier example:

```text
Uzzys Universe/
+-- MilkyWay/
    +-- Mastery/
        +-- Games/
            +-- Chess/
        +-- Languages/
            +-- French/
            +-- Igbo/
```

These are the same architecture. Only the names, total tier count, and number of grouping tiers change.

### README / Documentation Pattern

Create lightweight README files at each level so the system explains itself:

- Hub `README.md`: explains what the AI OS / second brain is, what the main tiers are, and that workspace repos are independent.
- First grouping tier `README.md`: explains what that tier contains.
- Each category/grouping folder `README.md`: explains what kind of workspaces belong there.
- Each workspace `README.md`: explains the actual project, its purpose, its repo, and any local setup notes.

The README files should be useful to a human and to future AI agents.

The hub should be able to work as a knowledge base for tools like Obsidian or other note systems. The user can keep references, documentation, prompts, architecture notes, and project maps in one place, while each actual project remains independently versioned.

### Documentation File Naming Rule

When creating the durable architecture document in the hub `Documentation/` folder, use the next available numbered filename prefix:

```text
Documentation/X.) AI OS Repo Architecture.md
```

`X.)` is not a literal filename. The agent must inspect the existing files in `Documentation/` and choose the next available number.

Examples:

- If no numbered documentation files exist, use `1.) AI OS Repo Architecture.md`.
- If the highest existing numbered documentation file is `2.) Existing Doc.md`, use `3.) AI OS Repo Architecture.md`.
- If the highest existing numbered documentation file is `10.) Existing Doc.md`, use `11.) AI OS Repo Architecture.md`.

Do not hard-code `1.)` without checking existing files. Do not overwrite an existing numbered documentation file.

## Part B: Git / GitHub Independent Repo Architecture

### Core Principle

The hub repo holds the **skeleton and the index**: folders, README files, documentation, prompts, and lightweight references.

Every actual workspace is its **own independent repo** with its own remote. The hub may track that workspace's final-tier `README.md` as a map marker, but it must ignore the workspace's real project contents.

Three hard rules make it work:

1. The hub tracks only each final-tier workspace `README.md`, if the user approves that placeholder pattern.
2. The hub `.gitignore`s everything else inside every workspace folder, so the hub never tracks a workspace's source files or project contents.
3. Each workspace is initialized on its own, with its own `.gitignore`, remote, and commit history.

A workspace's location on disk is independent of its repo identity. You can move a workspace folder later without renaming its GitHub repo, because the workspace's `.git` folder travels with it.

### Why This Architecture Works

1. **Everything is easy to find.** The AI OS hub becomes the organized map of the user's projects and knowledge.
2. **Each project stays clean.** Every workspace has its own history, issues, commits, and remote.
3. **The hub stays lightweight.** It does not become a giant repo containing every project.
4. **AI agents get better context.** README files tell agents what each folder is for.
5. **Knowledge tools can scan the whole system.** Obsidian or similar tools can see the map and notes in one place.
6. **GitHub stays modular.** The user can share one workspace repo without exposing the entire second brain.
7. **Nested repo problems are avoided.** The hub does not accidentally commit inner project repos.

### Non-Negotiable Git Rules

1. The hub repo tracks only the skeleton: folders, README files, indexes, instructions, prompts, documentation, and references.
2. The hub repo should track each approved final-tier workspace `README.md` as a README-only placeholder.
3. The hub repo must ignore everything else inside every actual workspace folder in the hub `.gitignore`.
4. Each workspace must be initialized as its own independent Git repo if it is meant to be versioned.
5. Each workspace must have its own GitHub remote if the user wants it on GitHub.
6. Never commit a workspace's actual project files into the hub repo.
7. Do not use submodules unless the user explicitly asks for pinned submodule behavior.
8. If a workspace is accidentally tracked by the hub, stop and explain the fix before doing anything.

### Hub `.gitignore` Pattern

The hub `.gitignore` must include a dedicated section for nested workspace repos.

Use the user's actual folder structure. Do not hard-code these example paths unless they are the user's real paths.

Example from a 4-total-tier setup:

```gitignore
# Nested workspace repos (README tracked by hub; contents tracked by their own repos)
MilkyWay/Tools/Workflows/**
!MilkyWay/Tools/Workflows/README.md

MilkyWay/Trading/Uzzy Ecosystem/**
!MilkyWay/Trading/Uzzy Ecosystem/README.md
```

Example for John:

```gitignore
# Nested workspace repos (README tracked by hub; contents tracked by their own repos)
Forge/CTrader Forge/Signal Builder/**
!Forge/CTrader Forge/Signal Builder/README.md

Forge/Python Forge/Data Lab/**
!Forge/Python Forge/Data Lab/README.md
```

The universal pattern is:

```gitignore
<path-from-hub-root-to-workspace>/**
!<path-from-hub-root-to-workspace>/README.md
```

Every actual working workspace must appear in the hub `.gitignore` before the hub repo is committed. If the user later adds a new workspace, update the hub `.gitignore` in the same pass. The hub should commit the workspace `README.md` only; the workspace repo should commit the real project files.

### Final-Tier Workspace README Tracking

This rule is mandatory and must be explained to the user before setup is called complete.

The hub should show every final-tier workspace as a README-only placeholder. The final-tier workspace `README.md` is the map marker. The workspace repo owns the real project contents.

When making or moving future workspaces:

1. Put the workspace in its final grouping-tier path.
2. Make sure the workspace has a `README.md`.
3. Add the matching ignore/README exception pair to the hub `.gitignore`.
4. Commit only the workspace `README.md`, parent tier `README.md` files if newly created, and the `.gitignore` update in the hub repo.
5. Commit real project files only inside the workspace's own repo.

When updating a final-tier workspace `README.md`, treat it as a shared boundary file:

1. Commit and push the README update inside the workspace repo first.
2. Return to the hub repo.
3. Commit and push the same README update in the hub repo.

Only the README follows this two-repo workflow. The workspace's source files, configs, build outputs, notes, and other project contents stay committed only inside the workspace repo unless the user explicitly says otherwise.

During Phase 7, ask the user:

> Do you want this final-tier workspace README rule added to your canonical agent contract file, such as `CLAUDE.md`, `AGENTS.md`, or another project instruction file?

If the user says yes, add the rule to the user's chosen canonical contract file. If the user says no or is unsure, keep the rule in the architecture document only and clearly note that choice.

## Git / GitHub Readiness Check

Before designing or initializing repos, confirm the user is ready to use Git and GitHub.

Do not assume the user has GitHub, Git, shell access, authentication, or agent-GitHub integration already working.

Ask and verify:

1. Does the user have a GitHub account?
2. Is Git installed on the user's computer?
3. Can the user's shell run `git --version`?
4. Is the user's Git identity configured with `git config user.name` and `git config user.email`?
5. Does the user know whether they want HTTPS or SSH GitHub authentication?
6. Can the user authenticate to GitHub from the shell or the agent environment?
7. If using Codex, Claude, Cursor, Antigravity, or another AI agent, is that agent connected to GitHub or able to use the user's GitHub CLI/session?
8. Is GitHub CLI (`gh`) installed and authenticated, if the setup plan depends on creating repos from the shell?

If any answer is "no" or unclear, pause the repo setup and guide the user through the missing prerequisite first. For a beginner, explain the difference between:

- **Git:** the local version-control tool on the computer.
- **GitHub:** the online remote hosting account.
- **Authentication:** the permission bridge that lets the shell or agent push to GitHub.

Do not start creating remotes or planning pushes until Git/GitHub readiness is confirmed.

## Safety Checks Before Any Commit

Before committing in the hub repo, run checks equivalent to:

```text
git status --short
git status --ignored --short
```

Confirm that workspace contents show as ignored by the hub and that no workspace source files are staged in the hub.

If the hub tracks final-tier workspace READMEs, confirm that only those README files are staged from inside workspace folders. Do not use `git add .` if it would stage nested workspace repos as embedded repositories or submodules.

Before committing in a workspace repo, confirm that the current directory is inside that workspace and that:

```text
git rev-parse --show-toplevel
```

points to the workspace, not the hub.

Whenever you are about to run `git add`, `git commit`, `git push`, `git rm`, or any command that changes Git state, tell the user which repo you are operating in and why.

## Recovery If A Workspace Was Accidentally Tracked By The Hub

If workspace files were added to the hub repo by mistake:

1. Stop.
2. Explain that the workspace should be independent.
3. Add the workspace path to the hub `.gitignore`.
4. Remove the workspace from the hub index without deleting local files, using the safe equivalent of:

```text
git rm -r --cached <workspace-path>
```

5. Commit the hub `.gitignore` cleanup.
6. Initialize or repair the workspace as its own independent repo.

Do not delete the workspace folder unless the user explicitly requests deletion.

![path-from-hub-root-to-workspace]/README.md
\`\`\`

1. Put the workspace in its final tier path.
2. Make sure the workspace has a `README.md`.
3. Add the matching ignore/README exception pair to the hub `.gitignore`.
4. Commit only the workspace `README.md`, parent tier `README.md` files if newly created, and the `.gitignore` update in the hub repo.
5. Commit real project files only inside the workspace repo.

When updating a final-tier workspace `README.md`:

1. Commit and push the README update inside the workspace repo first.
2. Return to the hub repo.
3. Commit and push the same README update in the hub repo.
